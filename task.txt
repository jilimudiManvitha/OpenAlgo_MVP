  strategy replay sequentially. Your current runner does not use the GPU, and 
  its 32 GB of GPU memory does not automatically extend your 32 GB system RAM.

  ## 2. Improve the runner before the full run                                
                                                                              
  For this workload, I recommend these changes:                               
                                                                              
  - Compile the expensive replay loop, verifying that entries, exits, partial 
    fills and costs match the existing engine.                                
                                                                              
  - Process independent stock-sessions in parallel, initially benchmarking 2–4
    worker processes.                                                         
                                                                              
  - Share indicator calculations across strategy variants wherever their      
    inputs match.                                                             
                                                                              
  - Save completed work frequently so an interruption loses little progress.  
  - Use one coordinated results writer, or separate worker outputs followed by
    a verified merge.                                                         
                                                                              
  These performance changes are not implemented in the current all-stock      
  runner. Increasing duckdb_threads alone will not parallelize its Python     
  strategy loop.                                                              
                                                                              
  Multiple workers can read the same immutable DuckDB snapshot in read-only   
  mode. DuckDB documents this access pattern.                                 
                                                                              
  ## 3. Keep memory and storage bounded                                       
                                                                              
  - Read small stock/date batches instead of loading the entire history.      
  - Start with the existing 2 GB DuckDB limit and measure total process       
    memory; Python objects consume additional RAM.

  - Increase workers only while memory and disk throughput permit.
  - Measure output growth—retaining every trade, fill and chart across nine   
    years may require much more space than the source database.

  The exact worker count depends on the i9 model and measured memory per      
  worker.

  ## 4. Benchmark before committing to nine years

  Run a small sample spanning early and recent years, including active trading
  days. Measure:

  - Stock-sessions processed per second.
  - Peak RAM.
  - Result storage per completed day.
  - Agreement with the existing engine.

  That provides a defensible completion estimate. The hardware specifications 
  alone cannot establish whether this takes hours, days or longer.
